## 1. Memory tree
Not a literal tree data structure — it's a pluggable engine model (local TinyCortex by default, or hosted/self-hosted CortexDB, or Supermemory/Mem0/Cognee/AgentMemory) accessed through TinyMemory's recall/fetch/store trait contract. Items are typed as documents, conversations, and learnings, tagged with source type (pdf/markdown/notion/github/web) and metadata (folder, repo, thread, source, time window). Source: https://tinyhumans.gitbook.io/openhuman/features/memory and https://github.com/tinyhumansai/tinymemory. WRITE: logged automatically pre-response (what the user said) and post-response (the reply plus a one-line result per tool call, never full tool arguments); a background job 'every few minutes' synthesizes beliefs/learnings from stored items; users can also add learnings manually. Source: https://tinyhumans.gitbook.io/openhuman/features/memory. READ: before each turn the engine recalls a short, token-budgeted 'memory pack' (learnings + documents + this agent's earlier turns + a little of other agents') that is injected into the model request only for that turn and never written into the visible chat; pack size (tokens), and counts of learnings/documents/turns are user-configurable. Source: same page. PRUNE/FORGET: an Explorer UI lets a user narrow down to specific stored items, open one, and hit 'Forget'; whole sources can also be forgotten in bulk. CortexDB itself is described as an append-only event log where 'forgets always name event ids' (i.e., forgetting is a new event, not physical deletion). Source: https://tinyhumans.gitbook.io/openhuman/features/memory and https://github.com/tinyhumansai/tinymemory README. PER-USER ISOLATION: each agent has its own memory id equal to its definition id; agent teams get a separate memory root (team:<id>); TinyMemory enforces this via a Namespace concept in its API crate. Data is 'scrubbed for secrets and personal identifiers before it leaves your machine.' Source: https://tinyhumans.gitbook.io/openhuman/features/memory; https://github.com/tinyhumansai/tinymemory.

## 2. Run journal
The 'run journal' phrase in the openhuman README ('durable, replayable run journals with per-call token and cost accounting') refers to the separate tinyagents engine it's built on, not a feature implemented inside openhuman itself. Source: https://tinyhumans.gitbook.io/openhuman/ (llms-full.txt overview section) and https://github.com/tinyhumansai/tinyagents. WHAT IS RECORDED: the tinyagents-session crate is described as a 'SQLite-backed store for session history, messages, tool calls, cost, and run lineage, plus JSONL transcripts.' Outcomes are modeled as a RunOutcome{output, pending_approvals, cancelled} struct. Source: https://github.com/tinyhumansai/tinyagents (README) and https://tinyhumans.gitbook.io/openhuman/developing/architecture/flows-on-tinyagents. STORAGE FORMAT: dual — SQLite for structured session/cost/lineage data plus JSONL transcripts; separately, openhuman's own flow layer persists live steps via a FlowRunObserver and exports durable graph observations to Langfuse via crates/openhuman-core/src/flows/tinyflows/langfuse_export.rs. Source: https://tinyhumans.gitbook.io/openhuman/developing/architecture/flows-on-tinyagents. APPEND-ONLY: checkpointing uses tinyagents::graph::SqliteCheckpointer with durable HITL (human-in-the-loop) resume, stored at <workspace_dir>/flows/checkpoints.db — checkpoints support resume and 'time travel' (replay across superstep boundaries), implying an append-style checkpoint log, though the docs don't explicitly label it append-only. Source: https://tinyhumans.gitbook.io/openhuman/developing/architecture/flows-on-tinyagents and https://github.com/tinyhumansai/tinyagents README. VIEWING: via Langfuse (external observability platform) for traces, and presumably via tinyagents' own topology/streaming-event export for local inspection; no dedicated in-app 'journal viewer' page was found in the docs I could reach. Source: same architecture page. EVALUATION/REPLAY: the graph engine explicitly supports checkpoint/resume/time-travel (replay), but I found no evidence it feeds an automated evaluation/scoring pipeline — that appeared out of scope per a separate (and less relevant) agent-observability.md page about openhuman's own E2E test harness, which is unrelated to the user-facing run journal. Source: https://tinyhumans.gitbook.io/openhuman/developing/agent-observability.md (noting this page is about dev-team E2E test artifacts, not the product run journal — flagged so it isn't conflated).

## 3. Install + connect flow
INSTALL: non-technical path is to download a native installer (macOS/Windows/Linux) from tinyhumans.ai/openhuman or the GitHub Releases page, open it, and accept OS permission prompts. Source: https://raw.githubusercontent.com/tinyhumansai/openhuman/main/gitbooks/overview/getting-started.md. Technical paths (INSTALL.md): `brew install --cask openhuman` (macOS), a `.deb` via apt for Debian/Ubuntu (arm64 variant noted), an AUR recipe `openhuman-bin`, a signed `.msi` for Windows, or curl/irm one-line install scripts — the docs explicitly warn these scripts 'do not ship a separate signature' and recommend native package managers instead. Source: https://raw.githubusercontent.com/tinyhumansai/openhuman/main/INSTALL.md. CONNECT: first screen is a sign-in step ('Sign in! Let's Cook') via social or standard login, with explicit note that 'third-party access requires explicit OAuth approval' (no ambient access granted). Service connections (e.g., Gmail) are added post-signup; API keys for 26 BYO-key LLM providers (OpenRouter, OpenAI, Anthropic, Google, Groq, Mistral, DeepSeek, Together, Fireworks, etc.) are pasted once via code (`.api_key("th_...")`) or an env var (OPENHUMAN_BACKEND_API_KEY), or local models are wired up by installing a runtime (Ollama/LM Studio/MLX/any OpenAI-compatible server) and pulling models independently. Memory engine is switched under Connections > Memory (hosted CortexDB signed-in, or self-hosted CortexDB endpoint+key). Source: https://raw.githubusercontent.com/tinyhumansai/openhuman/main/README.md and gitbooks/overview/getting-started.md. IMAGES/SCREENSHOTS: only two image paths were found referenced in the README: `./gitbooks/.gitbook/assets/demo.png` and `./gitbooks/.gitbook/assets/workflows.png` (both relative paths inside the repo). Source: https://raw.githubusercontent.com/tinyhumansai/openhuman/main/README.md. ## 4. Trust/safety
Tool results vs. instructions: the approval-gate doc does not explicitly state a policy that tool results are 'data, not instructions' for the model — it only documents the pre-execution approval gate, so this specific design point is unconfirmed/not found. Source: https://tinyhumans.gitbook.io/openhuman/features/approval-gate.md. ASK-FIRST/APPROVAL: yes — an approval gate is 'on by default,' parking any tool call with an external effect ('a purchase, a send, a delete') as NeedsConfirmation, and 'fails closed if you don't' respond. Commands are classified into five risk classes (Read, Write, Network, Install, Destructive) and three autonomy tiers (Read-only, Supervised [default], Full) gate which classes prompt vs. auto-run. Prompted calls show an Approval Request card (tool name, action summary, redacted command) with Approve-once / Always-allow / Deny options; unanswered requests auto-deny after a 10-minute timeout; pending requests persist in SQLite across restarts. Source: https://tinyhumans.gitbook.io/openhuman/features/approval-gate.md. TELEMETRY DEFAULT: no telemetry-default statement was found on the approval-gate page; a separate 'Privacy Mode' feature offers a one-switch local-only mode that blocks all cloud model calls, implying telemetry/cloud calls are otherwise on by default, but I did not find an explicit telemetry on/off statement to cite directly. Source: https://tinyhumans.gitbook.io/openhuman/features/privacy-mode.md (page existence confirmed via sitemap, not separately fetched/quoted this session — flagged as not independently verified).
