## 2. Memory ladder
Level 0, raw memories: `memory_units` rows (`api/alembic/versions/5a366d414dce_initial_schema.py`): `text`, `embedding` (pgvector, dim auto-detected), `context`, `event_date`, `occurred_start/end`, `mentioned_at`, `fact_type` (`world` | `experience`), `confidence_score`, `tags`, plus `entities`, `unit_entities`, `memory_links` (entity/temporal/causal graph). `retain` runs an LLM fact-extraction pass (`api/engine/retain/fact_extraction.py`, `fact_storage.py`), so every write costs one model call.
Level 1, observations: same table, `fact_type='observation'`, with `source_memory_ids[]` and `proof_count` (= distinct live sources). Built bottom-up by `api/engine/consolidation/consolidator.py`: a background job after each retain groups new memories by tag scope (`_consolidation_batch_key`), recalls nearby observations, and asks the LLM for `_CreateAction` / `_UpdateAction` / `_DeleteAction` per batch. Update = rewrite text + merge source ids + merge tags (`store.rewrite_observation`); delete = "superseded or contradicted" (`_execute_delete_action`). Optional pre-pass `_dedup_adjudicate` merges near-duplicates above `consolidation_dedup_threshold`. Each change appends a snapshot row to `observation_history`, capped by `observation_history_max_entries`.
Level 2, mental models: `mental_models` table (`api/alembic/versions/h3c4d5e6f7g8_mental_models_v4.py`): a standing question per bank whose answer is a JSONB document of `Observation` items with per-item fact attribution. Refreshed by `reflect` (`api/engine/reflect/agent.py`), in `full` or `delta` mode (`api/engine/mental_model_refresh.py`: `RefreshMode`, `MentalModelDeltaOperations`, `MentalModelRetraction`). Triggers: on demand, cron (`f2a7c9d4b168_add_mental_models_cron_index`), or `refresh_after_consolidation` when `compute_mental_model_is_stale` says a scope changed. "Knowledge pages" are mental models projected to markdown.
Decay/retention: no score decay. Time-awareness is computed, not stored: `compute_trend()` in `api/engine/reflect/observations.py` labels each observation `new | strengthening | stable | weakening | stale` from evidence timestamps (30-day recent / 90-day old windows). `access_count` was dropped (`e4a7c1b9d2f6`). Contradiction resolution is an LLM delete/rewrite, with `invalidated` memory units kept (`c9a1b2d3e4f5`).

## 3. Evidence model
- Observation-level (mental models): `ObservationEvidence {memory_id, quote (exact), relevance, timestamp}` and `Observation {title, content, evidence[], created_at}` with computed `trend`, `evidence_span`, `evidence_count` (`api/engine/reflect/observations.py`). The quote is required so a belief is verifiable against its source.
- Row-level: `source_memory_ids[]` + `proof_count` on the observation row; the LLM prompt sees each source's text/context/occurred dates (`_build_observations_for_llm`, consolidator ~l.3030). `observation_history` keeps pre-update snapshots. `confidence_score` exists on raw units but consolidation ranks on proof count and recency, not on it.
- Retrieval: `recall` runs semantic + BM25 + graph-link + temporal strategies in parallel, fuses with reciprocal rank fusion, cross-encoder reranks, trims to a token budget (`api/engine/memories/pg/recall.py`, `link_expansion.py`). Filters: `bank_id` (hard isolation), `fact_type`, tags/scopes. Evidence itself is not a ranking feature; `reflect` reads it when writing an answer.
- Tags are a security boundary: source tags are merged into the observation "so all contributors can see it" (consolidator ~l.2810).

## 4. Storage / embedded mode
- Hard requirement: **PostgreSQL + pgvector** (or Oracle 23ai). No SQLite/LanceDB/DuckDB backend; `api/engine/db/` has only `postgresql.py` and `oracle.py`.
- Embedded mode: `hindsight-all` bundles `pg0-embedded>=0.15.0` (a bundled Postgres binary, no install) and a daemon. `HindsightEmbedded(profile=...)` (`hindsight-all/hindsight/embedded.py`) auto-starts a local HTTP daemon and keeps data in `~/.pg0/instances/hindsight-embed-{profile}/`; `database_url` can point elsewhere. README's platform table marks Windows x86_64 as supported for embedded DB. So "one instance per drawer" = one `profile` (or one `bank_id` inside one profile; banks are strictly isolated). Each profile is its own Postgres process on its own port, though; two are heavier than one profile with per-person banks.
- Cost of "no Postgres for the person": partial. Nothing to install, but a Postgres server and a Python daemon run on the machine, hold ports, and need lifecycle care (the daemon no longer idles out).
- Embeddings: pluggable (`api/engine/embeddings.py`): `LocalSTEmbeddings` (sentence-transformers, default model from `config.DEFAULT_EMBEDDINGS_LOCAL_MODEL`, 384-dim in the initial schema, so a MiniLM/bge-small class model), `OnnxEmbeddings` (`local-onnx` extra), TEI, OpenAI, Cohere, Gemini, LiteLLM. Reranker also local or API.
- LLM: `retain`, consolidation and `reflect` all need a chat model (25+ providers incl. `anthropic`, `ollama`, `lmstudio`).
- Footprint (rough): pg0 Postgres ~100 MB on disk + a service process; `local-ml` pulls CPU torch + sentence-transformers (~1.5-2 GB); `local-onnx` is a few hundred MB. Plus one LLM call per retain and per consolidation batch.

## 5. What T63 / T57 should borrow
- Borrow the **evidence-with-exact-quote** shape (`ObservationEvidence`: source id, verbatim quote, timestamp) because a proposal must be checkable by a non-technical person; maps to the T63 proposal card ("3 times in 14 days" plus the three log rows it counted) and to `proposal_decision` events.
- Borrow **proof_count + computed trend** (counts over timestamps, no stored decay) because it is plain arithmetic over the append-only activity log, no model in the loop; maps to T63's repeat counter (new/strengthening = propose; stale = drop) and gives T57 a retention rule without a background job.
- Borrow **bank isolation + tag-scoped visibility** (one bank per person, tags merged so contributors can see derived items) because it matches per-person drawers and the T57 per-drawer role gate; maps to a `drawer_id` on every stored item and derived item.
- Borrow **observation_history as a capped snapshot table** instead of mutating in place, because our log is append-only and a proposal's earlier wording must stay auditable; maps to `proposal` rows that are only ever superseded, never edited.
- Borrow **"a model writes only the sentence, from counted facts"** (Hindsight's consolidation prompt gets structured sources, returns structured actions, sanitized via `sanitize_llm_output`) because tool results are data, not instructions; maps to T63's design (#277) and to the scrubber-first rule: facts pass the scrubber before any model sees them.
- Do not borrow the write path: LLM-extracted facts at retain time, background consolidation and refresh cron are three services the person would have to trust silently; they cross ask-first (#98) and the no-new-services rule.

## 6. Verdict
**Borrow ideas only; do not adopt as a dependency now.** Hindsight is MIT, active (release 0.10.2 the day before this scout), and its evidence and observation models are exactly the shape T63 needs, but it is a Postgres+pgvector service with an LLM in every write path. On Windows it can run without an install via pg0, but that still means a Postgres process, a daemon, ports and model downloads per person, which is against "no new services for the person to manage", and it ships nothing for the T57 question (SQLite/LanceDB-class embedded vectors). Re-evaluate for Phase 3 if T57 concludes a local Postgres is acceptable; the pin to use then is `hindsight-all==0.10.2` at commit `f2c33cc4…05ad`.
Open question for Braden: is a bundled local Postgres (pg0) per Windows machine an acceptable "no server" for Phase 3 drawers, or must drawers stay file/SQLite-based? That answer decides whether Hindsight is ever a candidate or stays a reference.
